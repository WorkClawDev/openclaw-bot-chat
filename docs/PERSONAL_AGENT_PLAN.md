# 个人工作助手 Agent 实施计划

本计划把 `test/openclaw-bot-chat` 中的独立 agent 发展为可日常使用的个人工作助手，覆盖聊天、文件处理、工具调用和持续任务。核心目标是：用户交办工作后，系统能可靠接收、执行、报告进度、保存结果，并在断线、重启、等待用户输入时继续保持正确状态。

评估日期：2026 年 10 月 3 日。代码基线：`master` 提交 `5328044` 加当前工作区已有的未提交改动。本文是实施方案；文中阶段和验收指标均为拟议目标，不能视为已实现或已通过验收。

## 一 当前结论

现有实现具备可复用的 agent 原型基础：MQTT 消息收发、会话路由、模型工具循环、本地文件工具、MCP、简单记忆、模型重试和上下文压缩。当前主要缺口在执行可靠性、状态持久化、工具权限、持续任务和交付体验。

建议继续演进独立 agent，保留 broker-first 架构，复用现有后端任务、文档、资产和客户端界面。第一版聚焦单个用户拥有一个主要助手、一个受控工作目录和少量可信工具；多用户托管、多个 agent 自主协作、插件市场列入后续版本。

近期最值得先完成的闭环是：用户发送文件和任务 → agent 展示执行状态 → 在授权目录内处理 → 提交可下载结果 → 用户确认完成。这个闭环应能经受进程重启和消息重复投递。

## 三 已确认的问题与优先级

### P0 启动入口与实际代码位置不一致

独立 agent 源码已经位于 `test/openclaw-bot-chat`，而 `scripts/test-agent.sh` 中的 `PLUGIN_DIR`、默认 handler、配置和状态路径仍指向 `plugins/openclaw-bot-chat`。当前旧目录下没有 `package.json`，依照默认脚本无法从该目录正常安装和构建。`manage-agents.sh` 和根 README 也保留旧路径；README 中的 testagent Compose profile 未出现在当前 Compose 配置中。

实施时先统一入口、开发命令、部署命令和数据目录，再做源码目录迁移。不要为了改名同时改 MQTT 协议、模型协议和存储格式。

证据：[启动脚本](../scripts/test-agent.sh)、[管理脚本](../scripts/manage-agents.sh)、[实际 agent 包](../test/openclaw-bot-chat/package.json)、[Compose 配置](../docker-compose.yml)。

### P0 文件工具权限默认值与隔离边界不足

`OPENAI_COMPAT_TOOL_EDIT_ENABLED=false` 控制的是 MCP 中被工具名规则识别为写入类的工具。本地 runtime 的文件写入工具由另一套配置创建，文件系统默认启用，读写 roots 为空时允许访问任意非隐藏路径。仅使用 `path.resolve` 和路径前缀检查，没有解析符号链接的真实目标。

本次使用临时目录中的自建文件进行了验证：允许目录中的符号链接可以读取目录外的测试文件；空写入 roots 允许在测试目录外侧写入新文件。没有访问真实敏感文件。这是可复现的权限边界缺陷。

Bash 目前只限制 `cwd`；这不能限制命令访问其他绝对路径、网络或继承的环境变量。`spawnSync` 还会阻塞 agent 所在进程；外层 `Promise.race` 不能可靠中断同步执行。MCP 超时同样不等于远端工具已经停止。

实施目标是一个统一的工具执行入口：身份校验、参数校验、能力策略、审批、隔离执行、取消、审计和结果归档均经过同一条路径。读取默认限定工作区，写入默认限定输出目录，执行命令必须进入隔离 runner。

证据：[本地工具](../test/openclaw-bot-chat/examples/openai-handler/local-runtime.cjs)、[MCP 权限规则](../test/openclaw-bot-chat/examples/openai-handler/mcp-runtime.cjs)、[handler 配置](../test/openclaw-bot-chat/examples/openai-compatible-handler.cjs)。

### P0 消息恢复可能跳过工作或重复产生副作用

启动时，runtime 将 bootstrap 返回的会话最新序号合并进本地 checkpoint；checkpoint 合并保留较新序号，然后历史补偿使用 `after_seq`。从代码路径判断，远端“已存在的最新消息”可能被当成本地“已经处理完成的消息”，跳过停机期间的未处理消息。需要优先用重启故障测试覆盖。

历史补偿当前只拉一批，缺少持续分页；去重依赖进程内最多 2000 条记录。回复发布在 checkpoint 保存之前，若在两者之间崩溃，重放可能生成新回复 ID、再次调用工具。前一条消息失败后，后一条消息仍可能前进并更新游标，需要处理失败消息与连续确认游标的关系。

实施时区分“服务端已接收”“worker 已持久接管”“run 已结束”“结果已发送”，建立持久 inbox 和 outbox，不能用一个 `last_seq` 表达所有状态。有副作用的工具必须提供幂等键或执行后核对；对结果不确定的外部操作进入人工确认，不能宣称通用 exactly-once。

证据：[启动与消息处理](../test/openclaw-bot-chat/src/runtime/bot.ts)、[checkpoint 合并](../test/openclaw-bot-chat/src/runtime/checkpoint.ts)、[回复 ID 生成](../test/openclaw-bot-chat/src/router/message.ts)。

### P0 生成配置进入版本跟踪

`test/openclaw-bot-chat` 中两个具名 `.test-agent.*.config.json` 已被 Git 跟踪，且含非空 accessKey 字段。本次未输出这些字段，也未验证密钥是否有效。

实施时需要检查是否为实际凭据；实际凭据应先轮换并确认消费者切换，再清理当前跟踪和忽略规则。历史清理应单独评估协作影响，不能把删除工作区文件当作撤销密钥。部署配置、状态和日志不得作为发布包内容。

### P1 会话编号持久化了 对话和记忆没有持久化

`SessionManager` 保存会话编号，`CheckpointStore` 保存消息位置，但默认 handler 的 `conversationHistory` 和 `sessionMemory` 都是内存 Map。进程重启会丢失模型上下文和便签。

历史先被截断为固定轮数，后面的历史摘要分支在正常追加流程中拿不到已被删掉的旧历史。另有请求内压缩逻辑，但它按字符及消息逐条压缩，缺少工具调用与结果成组保留的保证，并会把历史摘要放进 system 消息。

实施目标：原始消息与工具执行记录可持久查询，摘要单独保存并记录来源；预算按模型上下文能力计算；外部文件、工具输出和旧对话内容保留其来源与信任等级，不能因摘要处理被提升为系统指令。

证据：[会话映射](../test/openclaw-bot-chat/src/runtime/session.ts)、[内存历史与便签](../test/openclaw-bot-chat/examples/openai-handler/session-state.cjs)、[上下文构造与压缩](../test/openclaw-bot-chat/examples/openai-compatible-handler.cjs)。

### P1 持续任务尚未接入独立 agent

独立 agent 的 HTTP client 有任务队列、领取、进度、结果和失败方法，但 runtime 主流程只处理聊天消息，默认 handler 没有任务执行上下文。现有工具轮数和时间预算耗尽后抛错，不能保存步骤后继续。

后端已经有任务状态机、带数据库行锁的领取过程、结果审核和依赖关系；这些应保留。扩展侧已有轮询与执行 hook，可提取协议和契约测试复用，但不能把独立 agent 直接依赖完整 OpenClaw 宿主。

仍需新增每次执行的 run、worker 租约、心跳、步骤记录、重试次数、取消信号和失联恢复。同一 bot 的多个 worker 也必须竞争同一个 run 的执行权，不能仅凭 bot ID 判定可以继续。

证据：[独立 agent 任务 HTTP 方法](../test/openclaw-bot-chat/src/client/http.ts)、[独立 runtime](../test/openclaw-bot-chat/src/runtime/bot.ts)、[扩展任务轮询](../extensions/openclaw-bot-chat/src/runtime.ts)、[后端任务服务](../backend/internal/service/task_service.go)、[后端任务领取](../backend/internal/repository/task_repo.go)。

### P1 缺少用户可操作的执行过程与交付物

默认模型请求使用 `stream: false`，handler 返回最终文本；独立 agent 请求接口没有贯穿整个执行链的取消信号。用户难以判断当前是在思考、调用工具、等待权限，还是已经卡住。

图片 URL 输入已存在，应继续保留。通用文件处理需要补齐资产下载授权、格式识别、文本提取、内容限制、输出文件上传和预览。后端已有文档和资产服务，可复用，不必新建另一套文件系统。

需要把“请用户补充信息”和“请求操作批准”做成不同的持久等待状态。用户回复后恢复原 run；取消应停止工具和后续动作；长任务要能离开聊天页面后继续执行。

### P1 缺少针对独立 agent 的质量与运行保障

独立 agent 的 `package.json` 没有 test 脚本，TypeScript include 仅覆盖 `src`，核心 `examples/openai-handler/*.cjs` 不在类型检查范围。存在 JSON 日志基础，但没有完整的 run 成功率、工具错误率、排队时延、token 用量和预算账本。

部署脚本以测试容器方式运行并挂载整个仓库，缺少专门的最小权限运行配置、worker 健康检查和发布回滚流程。生产化前还要落实进程排空、MCP 子进程回收、状态备份和恢复验证。

## 四 第一版的产品边界

第一版围绕以下真实工作场景验收：

1. 连续多轮沟通，同一任务可补充要求；重启后记得任务约束与已经完成的步骤。
2. 上传文本、Markdown、PDF、DOCX、CSV 或 XLSX，读取内容并生成摘要、整理清单或新的文档。首批 PDF 可限定为可提取文本的文件，扫描件明确提示需要 OCR。
3. 在授权工作目录内查找、整理和编辑文件，修改前展示目标及必要的 diff，输出可下载成果。
4. 调用少量已配置的 MCP 工具，明确显示可用、需要授权和不可用状态；单个工具服务失效不阻断基础聊天。
5. 执行一个 5 至 30 分钟的多步骤任务，能看进度、补充信息、停止、重试，并提交可验收结果。
6. 保存用户明确要求记住的偏好，支持查看、修改和删除；设置一次性提醒或周期任务，按用户时区执行。

第一版默认一个任务同时只有一个执行者；同会话顺序执行，不同会话设总并发上限。编程可作为文件与命令工具支持的工作类型，完整 PR 自动交付流程列入后续扩展。

涉及对外发送、公开发布、删除或覆盖重要文件的操作，按明确授权和操作范围执行。普通聊天、授权目录内的只读操作、已经授权的低风险步骤不反复打断用户。任务结果审核与执行权限审批是两套流程。

## 五 建议的技术结构

| 模块 | 职责与边界 |
| --- | --- |
| Web 和 iOS | 聊天、任务进度、工具状态、审批、补充输入、结果预览、记忆与计划任务管理 |
| MQTT broker | 保留现有消息主通道，传递聊天和执行事件通知；支持断线后以持久记录补偿 |
| Go backend | 认证、owner 与 bot 权限、任务和 run 状态、租约、审批、资产、记忆、计划任务、事件历史 |
| PostgreSQL | 保存权威业务状态、inbox、outbox、run、步骤和审计记录；Redis 可作唤醒与缓存，不能是唯一任务事实来源 |
| Agent worker | 模型适配、上下文构造、有限步执行、工具调度、预算、心跳、恢复与最终结果校验 |
| Tool runner | 执行文件解析、写入与命令；按工作区隔离，最小挂载、最小环境变量、资源与网络限制 |
| MCP adapter | 工具发现、参数 schema、连接管理、健康状态；所有执行仍经过统一策略与审计 |

建议逐步将默认 handler 转为正式 TypeScript 模块，最终归入 `agent/`。第一阶段先在现有目录修复入口和加测试，之后一次性迁移并保留旧脚本兼容入口。`extensions/openclaw-bot-chat` 继续作为 OpenClaw 通道适配层。

业务层继续使用现有 `Task`、`TaskEvent`、`Document` 和资产模型。新增记录以单一事实来源为原则，不为 agent 复制一套独立的任务数据库。

### 需要新增的持久对象

| 对象 | 关键字段或约束 |
| --- | --- |
| AgentRun | owner、bot、conversation、task、触发 message、状态、attempt、worker、租约到期、版本号、预算、取消请求 |
| RunStep 和 ToolCall | 顺序、工具名称与版本、参数摘要、输入输出引用、幂等键、起止时间、结果或错误、外部操作凭据引用 |
| RunEvent | 单调递增事件序号、run ID、事件类型、客户端可见摘要；支持从指定序号补读 |
| Inbox 和 Outbox | 入站唯一键、持久接管状态；出站稳定消息 ID、待投递状态、重试信息 |
| Approval | run、操作参数 hash、资源范围、审批人、有效期、单次或限定范围授权、决定与审计 |
| Artifact | 复用资产存储，补 run 和 task 关联、文件名、MIME、大小、hash、版本和访问控制 |
| Memory | owner 与作用域、内容、来源、是否由用户确认、更新时间、过期和删除状态 |
| Schedule | 时区、规则、下一触发时间、暂停状态、错过执行策略、唯一 occurrence ID、关联任务 |

增加数据库迁移时需要先验证旧客户端、旧任务数据和老 worker 的兼容性。新增接口放在现有认证体系下；审批决定必须由有权限的用户身份提交。

### Run 状态与恢复规则

run 状态建议为 `queued`、`running`、`waiting_input`、`waiting_approval`、`paused`、`succeeded`、`failed`、`cancelled`。Task 继续使用现有业务状态；run 成功提交结果后，Task 进入 `awaiting_review`，用户接受后才进入 `completed`。

关键约束：

- 聊天长任务和任务页派发最终进入同一执行器，避免两条链路各自实现恢复与权限。
- 一个任务可以有多个 run attempt，但同一时刻只有一个有效租约；写进度、提交结果时校验租约版本，防止旧 worker 回写。
- 等待用户时持久保存状态并释放执行资源，不能占着模型请求等待。
- 取消传播到模型请求、工具进程、MCP 调用和后续调度；若外部操作无法撤销，显示已产生的结果及剩余工作。
- 先记录工具意图，再调用工具并保存结果。重启后根据工具的幂等能力决定安全重试、核对结果或等待用户处理。
- 预算达到阈值后保存已完成步骤和成果，进入可理解的停止或等待状态；禁止通过反复自建子任务绕过预算。
- MQTT 消息确认、后端持久化与客户端显示分别记录；UI 通过事件序号去重和补偿。

## 六 分阶段实施与验收

下面按一个熟悉代码库的全职工程师估算，共约 29 至 44 个工作日，即 6 至 9 周。估算包含开发与集成验证，实际取决于模型服务、文件格式、运行平台及现有本地改动整合成本；不属于交付承诺。每阶段都应形成可独立 review 和回滚的改动。

| 阶段 | 工作量估算 | 交付内容 | 通过条件 |
| --- | --- | --- | --- |
| 0 运行基线 | 2 至 3 天 | 统一路径和 Node 版本；配置校验、doctor；独立 agent 测试入口；配置与密钥整改方案 | 干净 checkout 可按文档安装、启动、停止；缺配置时给出明确诊断；不依赖旧目录残留文件 |
| 1 工具边界 | 4 至 6 天 | 统一 Tool Registry 与 Policy；schema 校验；默认目录；审批持久化及最小 UI；隔离 runner；异步子进程和取消 | 符号链接越界、隐藏凭据、未批准写入、shell 越界、过期审批全部被阻断；普通授权操作不重复询问 |
| 2 持久执行基础 | 4 至 6 天 | 保存上下文和步骤；修复 checkpoint；inbox、outbox、稳定回复 ID；分页补偿；队列上限、优雅退出 | 断网恢复超过一页消息不漏；任意中断点恢复不重复已确认副作用；重启后保留会话和任务约束 |
| 3 持续任务 | 5 至 7 天 | 接通现有任务队列；run 状态机、租约、心跳、取消、等待输入、重试；结果校验和审核 | Web 或 iOS 派发任务后自动执行；中途重启可继续；两个 worker 不重复执行；结果正确进入审核 |
| 4 文件与工作成果 | 4 至 6 天 | 资产下载授权；文本、PDF、DOCX、CSV、XLSX 处理；图片能力保留；输出上传；文档服务和 MCP 生命周期整合 | 完成约定文件工作场景，产物可在 Web 和 iOS 打开；解析失败有可见原因；大文件、错误 MIME 和压缩包限制生效 |
| 5 记忆与计划任务 | 3 至 5 天 | 用户偏好、项目事实、摘要持久化；来源和删除；一次性与周期任务、时区、暂停、错过执行策略 | 重启保留记忆，删除后不会被检索；计划任务每次 occurrence 只创建一个任务；重启补执行遵循用户设置 |
| 6 日常交互完善 | 4 至 6 天 | 模型流式输出、工具过程、任务卡片、补充输入、停止、审批恢复、产物预览、错误与预算展示 | 两端能明确显示当前状态；取消反馈及时；重连补齐事件且最终消息不重复；错误可重试且保留已有成果 |
| 7 运行与发布验收 | 3 至 5 天 | 专用镜像、非 root、最小挂载、健康检查、日志脱敏、指标、预算账本、备份恢复、发布回滚、真实任务评测 | 故障测试与真实场景通过；持续运行稳定；可以从备份恢复并回滚版本；形成验收记录 |

阶段 1 和 3 必须各自交付最小可用的审批与进度界面，不能等到阶段 6 才让用户看到等待状态。阶段 6 负责完成体验和跨端一致性。

建议里程碑：阶段 0 至 3 后内部试用持续任务；阶段 4 至 6 后进入个人日常试用；阶段 7 通过后再作为稳定版本使用。第一版不要求同时引入向量数据库、多 agent 编排或通用插件市场。

## 八 验收场景和质量门槛

### 必须通过的端到端场景

| 场景 | 操作 | 预期结果 |
| --- | --- | --- |
| 多轮继续 | 给出目标，补充约束，重启 worker 后继续 | 保留目标、约束和已完成步骤，不依赖旧进程内存 |
| 离线补偿 | worker 离线后产生超过 200 条消息 | 分页补齐；未处理消息可追踪；游标不越过尚未持久接管的消息 |
| 重复消息 | 同一触发消息重投 100 次 | 只创建一个逻辑 run；相同工具副作用不重复 |
| 崩溃窗口 | 分别在工具执行前后、回复发送前后、checkpoint 更新前后终止进程 | 幂等工具安全恢复；不确定操作显示待核对；不伪报完成 |
| Worker 竞争 | 两个 worker 同时处理同一个 bot 的任务 | 只有有效租约持有者执行和更新；旧 worker 的结果不能覆盖新结果 |
| 权限边界 | 尝试目录穿越、符号链接、绝对路径 shell、过期或被修改参数的审批 | 所有未授权路径与动作被拒绝，审计记录完整 |
| 外部内容注入 | 文件和工具结果中包含索要凭据或改变系统指令的文本 | 作为工作数据处理，不能获得额外权限或写入高信任记忆 |
| 停止执行 | 运行模型、文件工具和长命令时点击停止 | 受控进程停止，后续工具不再调度；无法撤销的动作如实显示 |
| 文件交付 | 上传 PDF 和表格，要求摘要与汇总文件 | 正确解析或明确报错，交付真实文件，链接权限正确 |
| 结果审核 | agent 提交成果，用户拒绝并补充要求 | Task 保留审核语义，新 attempt 关联旧结果，不重复已经确认的动作 |
| 服务故障 | 模型 429、超时、MCP 崩溃、broker 或 backend 断开 | 有限重试与退避，显示状态和可恢复错误，不无限耗费预算 |
| 定时执行 | 在用户时区设定任务，触发前后重启服务 | 每次 occurrence 去重，漏跑策略一致，可以暂停和取消 |
| 记忆删除 | 保存并使用偏好后删除 | 默认检索、缓存和摘要引用不再恢复该记忆；备份保留策略明确 |

### 建议的初始指标

以下是发布门槛提案，需在固定部署环境、固定模型配置和固定数据集上测量：

- 建立 40 个代表性个人工作任务，覆盖聊天、文件、工具、长任务和计划任务；至少 36 个无需人工修改结果即可完成。预期权限拒绝单独计为正确处理。
- 所有确定性的权限、重复投递、取消、恢复和隔离测试通过；已知会漏任务、越权或重复副作用的缺陷阻断发布。
- 在约定并发下，95% 的请求在 2 秒内显示“已接收或排队”，不把模型首字延迟混入该指标。
- 受控本地工具的取消在 5 秒内反馈并终止执行；远端工具单独标明取消支持和实际状态。
- 每个 run 都能查询执行步骤、模型用量或“用量未知”、预算状态、错误、产物与授权记录。
- 连续运行 72 小时，包含模型、MCP、网络和 worker 重启的故障注入；未出现任务静默丢失、进程资源持续泄漏或跨工作区访问。
- 备份恢复和上一版本回滚各完成一次实测，不以脚本存在作为通过。

性能与成本先建立基线再优化。记录模型 token 和请求时长，工具计数、排队时长、错误分类、预算停止次数及用户接受率；模型服务不返回 usage 时必须标为未知或估算，不能记为零。

## 十 实施前需要确定的运行参数

这些选择不影响当前缺口判断，可在阶段 0 落定：

- Worker 运行在用户电脑、私有服务器还是两者结合；这决定文件访问和离线行为。
- 默认允许读取的工作目录、允许写入的输出目录，以及首批接入的 MCP 服务。
- 默认模型服务、可接受的单任务和每日预算；用真实任务评测后再调整配置。
- 第一版文件格式的具体优先级，以及是否把 OCR 和语音输入纳入首发。
- 计划任务错过执行时选择补跑一次、跳过还是提示；通知只在有结果、失败或需要用户处理时发送。

当前推荐按单用户、单主要 worker、一个受控工作区、现有后端作为权威状态源开始，先完成可恢复的文件任务闭环，再扩展外部服务和更多主动能力。
