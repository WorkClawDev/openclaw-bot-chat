# OpenClaw Documents Full-stack MVP — Codex 需求文档 v0.2

> 定位：这是一份交给 Codex 的「前后端一体需求文档」，不是代码设计文档。  
> 原则：描述产品目标、业务流程、能力边界、验收标准和执行顺序；具体代码结构、数据库结构、API 命名、iOS 组件拆分、后端模块划分由 Codex 在审计现有仓库后决定。  
> 核心目标：让 OpenClaw Bot 生成的长内容从聊天气泡升级为持久化 Document Object，用户可以在 iOS App 中稳定查看、保存、编辑、找回，并由后端真实持久化。

---

## 1. 背景

OpenClaw Bot 当前主要是机器人聊天产品，已经支持：

- 文本消息
- Markdown 消息
- 图片消息
- 语音消息

现在需要新增一种更稳定的内容承载方式：**文档对象 Document Object**。

机器人不应该只把长内容塞进聊天流，而应该可以创建一份完整文档。用户在聊天里收到文档卡片，点击后进入文档页面查看、编辑、导出或继续让机器人修改。文档应保存在用户空间中，用户可以之后从「我的文档」找回。

这个需求需要同时包含：

- iOS App 页面与交互
- 后端文档持久化能力
- 聊天消息与文档对象的关联
- Bot 创建/更新文档的后端能力
- 原型图与产品说明
- 测试、验收和回归保护

---

## 2. 这份文档对 Codex 的要求

Codex 不能直接按照本文臆造目录、模型、数据库、接口格式。Codex 必须先审计当前仓库，再基于已有工程约定实施。

Codex 需要自行判断：

- iOS App 使用 SwiftUI、UIKit 还是混合架构
- 当前聊天消息如何建模
- 当前网络层如何请求后端
- 当前是否已有用户系统、鉴权、Workspace、文件存储、数据库迁移体系
- 当前后端使用什么语言、框架、ORM、路由、测试框架
- 当前项目是否已有 feature flag、环境配置、CI、测试命令
- 当前是否已有 Bot tool / action / function call / plugin 机制

本文只定义「必须实现什么」。具体「怎么实现」由 Codex 根据现有仓库决定。

## 3. 一句话产品目标

让 OpenClaw Bot 能够创建、发送、保存、查看、编辑和管理长文档，使机器人生成的内容变成用户空间里的稳定资产，而不是一次性聊天消息。

## 4. MVP 用户故事

### 4.1 Bot 创建文档

作为用户，我可以在聊天中说：

> 帮我生成一份 AI 编程学习路线，并保存成文档。

Bot 应创建一份文档，并在聊天中返回文档卡片。用户点击卡片可以打开完整文档。

### 4.2 用户查看文档

作为用户，我可以在 iOS App 中打开文档详情页，看到完整标题、正文、章节结构、更新时间和创建来源。

### 4.3 用户编辑文档

作为用户，我可以修改文档标题和正文，保存后内容应真实写入后端。退出 App 或刷新后仍能看到修改后的内容。

### 4.4 用户找回文档

作为用户，我可以进入「我的文档」或类似用户空间页面，看到自己历史创建或 Bot 生成的文档。

### 4.5 用户从聊天继续修改文档

作为用户，我可以在聊天中基于某份文档继续发起修改请求，例如：

> 把这份文档的第二部分写得更详细。

MVP 不要求实现复杂的局部协同编辑，但系统必须支持「聊天消息引用某份文档」这一产品能力。

## 5. MVP 范围

### 5.1 必须实现

#### 产品能力

- 聊天中显示文档卡片。
- 文档卡片可以打开文档详情页。
- App 内有「我的文档」或等价入口。
- 用户可以查看自己的文档列表。
- 用户可以查看完整文档内容。
- 用户可以编辑文档标题和正文。
- 用户保存编辑后，内容真实持久化到后端。
- 文档可以被 Bot 创建，至少要有一条端到端路径能够验证 Bot 生成内容变成文档。
- 文档有基础状态信息：标题、摘要或预览、更新时间、创建来源、文档类型。
- 支持基础错误状态：加载失败、保存失败、文档不存在、权限不足、空文档。
- 新能力必须受 feature flag 或等价灰度机制控制，不能破坏现有聊天能力。

#### 后端能力

- 持久化保存文档。
- 按当前用户隔离文档数据。
- 提供文档列表读取能力。
- 提供单篇文档读取能力。
- 提供文档创建能力。
- 提供文档更新能力。
- 提供文档删除、归档或等价隐藏能力。
- 支持聊天消息或 Bot 结果引用文档。
- 支持最小可用的鉴权和所有权校验。
- 提供自动化测试或可重复验证脚本，证明文档创建、读取、更新、列表能力可用。

#### iOS 能力

- 接入真实后端，不以 Mock Data 作为最终交付。
- Mock Data 可以用于 Preview、开发和离线演示，但最终 MVP 必须能访问真实后端。
- 文档列表页必须展示真实用户文档。
- 文档详情页必须展示真实后端内容。
- 文档编辑保存必须调用真实后端。
- 聊天文档卡片必须能引用真实后端文档。
- 网络失败、空状态、加载中状态必须有明确 UI。

#### 原型能力

- Codex 在实现前先生成或准备 ImageGen 原型提示词。
- 原型至少覆盖：聊天文档卡片、我的文档、文档详情、文档编辑、导出与分享、多维表格占位。
- 如果当前环境不能直接生成图片，Codex 必须输出完整 ImageGen prompt 和 wireframe spec，不得因此停止后续开发。

## 6. MVP 暂不实现

MVP 不要求实现以下能力：

- 多人实时协作。
- 飞书文档级别的完整富文本编辑器。
- Office 原格式在线编辑。
- 完整 PDF 编辑。
- DOCX / XLSX / PPTX 双向编辑。
- 多维表格完整数据库能力。
- 复杂团队权限。
- 评论、批注、协作者光标。
- 文档版本差异对比。
- 全文搜索和语义搜索。
- 工作流自动化。
- 仪表盘。

这些能力可以在产品文档中作为后续版本规划，但不要阻塞 MVP。

## 7. 文档类型范围

MVP 聚焦一种核心文档：**原生文本/Markdown 文档**。

需要支持：

- 标题
- 正文
- Markdown 风格的段落、列表、标题、代码块
- 基础元信息
- 从 Bot 生成内容创建文档
- 从 App 编辑文档

MVP 可以展示以下占位能力，但不要求真实完整实现：

- PDF 导出
- 分享链接
- 多维表格
- 文件型文档
- Office 文档

占位能力必须明确标注为「即将支持」或 disabled，不能假装已经完成。

## 8. 核心业务流程

### 8.1 Bot 生成文档流程

1. 用户在聊天中请求 Bot 生成长文档。
2. Bot 或后端识别该结果应保存为文档。
3. 后端创建文档并保存内容。
4. 聊天流中显示文档卡片。
5. 文档卡片包含足够信息，让用户知道这是一份可打开、可保存、可继续修改的文档。
6. 用户点击卡片后进入文档详情页。
7. 文档详情页从后端读取完整内容。

验收标准：

- 生成文档后，刷新 App 或重新登录后，文档仍然存在。
- 文档卡片不只是静态 UI，必须引用真实文档。
- 如果文档创建失败，聊天中不能显示一个无法打开的假卡片。

### 8.2 用户空间查看流程

1. 用户进入「我的文档」或等价入口。
2. App 请求后端获取当前用户文档列表。
3. 页面展示文档标题、摘要或内容预览、更新时间、创建来源。
4. 用户点击某一项进入详情。
5. App 请求后端获取完整文档。

验收标准：

- 列表内容来自后端。
- 当前用户只能看到自己的文档。
- 没有文档时显示空状态。
- 加载失败时显示错误状态和重试入口。

### 8.3 用户编辑流程

1. 用户打开文档详情。
2. 用户点击编辑。
3. App 进入编辑模式或编辑页面。
4. 用户修改标题或正文。
5. 用户保存。
6. App 调用后端更新文档。
7. 后端保存成功后，App 显示更新后的内容。

验收标准：

- 保存后刷新页面，修改仍存在。
- 保存失败时保留用户未保存内容，不应静默丢失。
- 取消编辑时应避免误保存。
- 并发冲突如果暂不完整解决，至少要有明确的失败或覆盖策略。

### 8.4 聊天继续修改流程

1. 用户在文档卡片或文档详情页触发「继续修改」。
2. App 回到聊天上下文，携带文档引用或将文档上下文注入下一条请求。
3. 用户提出修改要求。
4. Bot 基于指定文档生成修改结果。
5. 后端更新文档或创建新版本。
6. App 显示修改完成状态。

MVP 可简化：

- 允许先把文档引用带回聊天输入框。
- 允许先支持整篇文档覆盖式更新。
- 不要求精确到 block 的局部编辑。

验收标准：

- 用户能明确知道当前正在修改哪份文档。
- 修改结果不能丢失原文档关联。

## 9. 页面需求

### 9.1 聊天文档卡片

目标：让用户在聊天流中识别这是一份持久化文档，而不是普通 Markdown 消息。

必须展示：

- 文档标题
- 摘要或前几行预览
- 文档类型
- 更新时间或创建时间
- 打开入口
- 继续修改入口
- 导出或分享入口，可以是占位

交互要求：

- 点击卡片打开文档详情。
- 点击继续修改后，用户应回到聊天上下文，并能针对这份文档提需求。
- 如果文档不存在或用户无权限，展示清晰错误。

### 9.2 我的文档

目标：让用户找回历史文档。

必须展示：

- 文档列表
- 最近更新排序
- 空状态
- 加载状态
- 错误状态
- 搜索框可以先做 UI 占位，若未接后端搜索必须明确只是本地过滤或暂不可用

可选展示：

- Bot 生成标签
- 草稿标签
- 文档类型筛选

### 9.3 文档详情

目标：稳定查看完整文档。

必须展示：

- 标题
- 更新时间
- 创建来源
- 正文内容
- 编辑入口
- 分享/导出入口，可以部分占位

内容展示要求：

- 长文档可滚动。
- Markdown 基础格式可读。
- 深色模式和浅色模式都可读。
- 空文档有明确提示。

### 9.4 文档编辑

目标：让用户完成最小可用编辑。

必须支持：

- 修改标题
- 修改正文
- 保存
- 取消
- 保存中状态
- 保存失败状态

MVP 不要求：

- 类飞书的块编辑器。
- 多人协作。
- 复杂格式工具栏。
- 图片拖拽上传。

### 9.5 导出与分享

目标：提供未来能力入口，并先完成一个真实可用的轻量导出能力。

MVP 至少实现其一：

- 复制 Markdown
- 系统分享 Markdown 文本

可以占位：

- 导出 PDF
- 分享链接
- 保存到文件

占位项必须明确标注当前不可用或即将支持。

### 9.6 多维表格占位

目标：为未来类似飞书多维表格的能力留出产品入口，但不在 MVP 中实现完整功能。

必须展示：

- 这是未来结构化数据文档能力。
- 表格、看板、日历等视图是未来能力。
- 当前不可误导用户以为已经支持完整数据库功能。

## 10. 后端需求

### 10.1 持久化

后端必须真实保存文档。保存介质、数据库、ORM、迁移方式由 Codex 根据现有后端工程决定。

要求：

- 文档创建后可再次读取。
- 文档更新后可再次读取更新内容。
- 文档删除或归档后不再出现在默认列表中。
- 服务重启后文档不应丢失。
- 测试环境和开发环境应有可重复验证方式。

### 10.2 用户隔离与权限

后端必须保证当前用户只能访问自己有权限的文档。

要求：

- 列表接口只返回当前用户可见文档。
- 详情读取需要校验权限。
- 更新文档需要校验编辑权限。
- 删除或归档需要校验权限。
- 未登录或鉴权失败时返回明确错误。
- 无权限访问时返回明确错误。

MVP 可以只支持私有文档，不要求团队协作权限。

### 10.3 文档创建

后端必须支持至少两种创建来源：

- 用户主动创建。
- Bot 生成内容后创建。

要求：

- 创建时至少包含标题和正文。
- 标题缺失时应有合理默认值。
- 正文为空时应允许草稿或返回明确错误，具体遵循现有产品风格。
- 创建成功后返回足够信息给 iOS 展示文档卡片和列表项。

### 10.4 文档读取

后端必须支持：

- 当前用户文档列表。
- 单篇文档详情。

要求：

- 列表应适合移动端展示，不必返回完整正文。
- 详情应返回完整正文。
- 更新时间必须准确更新。
- 已删除或无权限文档应有明确错误。

### 10.5 文档更新

后端必须支持更新：

- 标题
- 正文
- 基础状态，例如归档或删除

要求：

- 更新后更新时间变化。
- 保存失败不能产生部分损坏数据。
- 如果后端已有乐观锁、版本号或更新时间冲突机制，应复用现有机制。
- 如果没有并发控制，Codex 需要记录风险，并实现一个可接受的 MVP 策略。

### 10.6 聊天消息与文档关联

后端或消息系统必须支持聊天中的文档卡片引用真实文档。

要求：

- 文档卡片能够携带文档引用。
- 打开卡片时能够读取对应文档。
- 文档删除或无权限时，App 应显示明确错误。
- 不能只在前端写死一张卡片。

具体是扩展消息模型、增加消息附件、增加 metadata，还是使用已有 rich content 机制，由 Codex 审计后决定。

### 10.7 Bot 集成

MVP 必须具备一条能验证的 Bot → Document 路径。

可以采用以下任一方式，具体由 Codex 根据现有系统决定：

- Bot 回复流程中触发文档创建。
- Bot tool/action/function call 创建文档。
- 后端提供内部服务让 Bot 写入文档。
- 开发环境提供一个可模拟 Bot 创建文档的路径，用于端到端验收。

验收时必须证明：

- Bot 生成内容可以变成后端文档。
- iOS 可以打开这份文档。
- 文档不是只存在于本地 Mock。

### 10.8 错误处理

后端必须区分至少以下错误：

- 未登录
- 无权限
- 文档不存在
- 请求内容无效
- 保存失败
- 服务内部错误

iOS 必须把这些错误转换成用户可理解的提示。

### 10.9 安全与隐私

要求：

- 不得把用户文档内容写入无保护日志。
- 不得在仓库中提交密钥。
- 不得绕过现有鉴权体系。
- 如果使用外部图像生成服务生成原型图，只能通过环境变量读取密钥。
- 文档内容属于用户数据，应遵守项目现有隐私和数据处理约定。

## 11. iOS 与后端集成需求

### 11.1 数据来源策略

开发阶段可以使用 Mock Data，但最终 MVP 必须接真实后端。

Codex 应实现或接入现有数据访问层，使 iOS 页面支持：

- 加载真实文档列表
- 加载真实文档详情
- 保存真实文档修改
- 从聊天卡片打开真实文档

如果后端暂时不可用，Codex 可以保留 mock fallback，但必须在文档中明确：

- 当前使用真实后端还是 mock
- 如何切换
- 哪些功能仍未接真实后端

### 11.2 状态处理

iOS 必须处理：

- 初次加载
- 下拉或手动刷新，可选
- 加载失败
- 空列表
- 文档不存在
- 保存中
- 保存失败
- 保存成功
- 无权限

### 11.3 兼容现有聊天能力

新增文档卡片不能破坏：

- 普通文本消息
- Markdown 消息
- 图片消息
- 语音消息
- 当前消息列表滚动行为
- 当前输入框行为
- 当前会话状态

### 11.4 Feature Flag

新增 Documents 能力必须可关闭。

要求：

- 默认策略由 Codex 根据项目现有环境决定。
- 关闭后不应影响现有聊天功能。
- 打开后可进入文档页面并使用文档卡片。

## 12. ImageGen 原型图需求

### 12.1 目标

在编码前，先生成或准备一张 iOS 产品原型图，帮助确认界面方向。

Codex 应优先生成：

- 一张包含 6 个 iPhone 页面并排展示的高保真原型图。

如果不能直接调用 ImageGen，则必须输出：

- 完整 ImageGen prompt。
- 每个页面的 wireframe 说明。
- 页面之间的跳转关系。

不能因为无法生成图片而停止后端或 iOS 实现。

### 12.2 原型图页面

需要覆盖 6 个页面：

1. Chat with Document Card
2. My Documents
3. Document Detail
4. Edit Document
5. Export and Share
6. Base Preview

### 12.3 ImageGen 主提示词

```text
生成一张高保真 iOS App 原型图，展示 OpenClaw Documents MVP 的 6 个 iPhone 页面。整体风格为现代 AI 助手应用，深色优先，同时兼容浅色设计。界面干净、紧凑、可信赖，像真实可实现的 iOS App 截图，不要做营销海报，不要夸张插画。

画面包含 6 个并排的 iPhone 15 Pro 屏幕，每个屏幕顶部有页面标题：
1. Chat with Document Card
2. My Documents
3. Document Detail
4. Edit Document
5. Export and Share
6. Base Preview

设计要求：
- 使用 iOS safe area、navigation bar、bottom sheet、rounded card。
```

## 14. 端到端验收场景

最终交付必须至少跑通以下场景。

### 场景 A：Bot 创建文档

1. 用户请求 Bot 生成一份学习路线。
2. 系统创建真实后端文档。
3. 聊天中出现文档卡片。
4. 用户点击卡片。
5. iOS 打开真实文档详情。
6. 用户退出再回来，文档仍存在。

### 场景 B：用户空间找回文档

1. 用户进入我的文档。
2. 看到刚才 Bot 创建的文档。
3. 点击进入详情。
4. 内容完整显示。

### 场景 C：编辑并持久化

1. 用户打开文档详情。
2. 用户修改标题或正文。
3. 用户保存。
4. App 显示保存成功。
5. 用户刷新或重启 App。
6. 修改后的内容仍存在。

### 场景 D：权限隔离

1. 用户 A 创建文档。
2. 用户 B 不能从列表或详情读取用户 A 的私有文档。
3. 后端返回明确无权限或不存在错误。

### 场景 E：现有聊天不回归

1. 普通文本消息仍可发送和展示。
2. Markdown 消息仍可渲染。
3. 图片消息仍可展示。
4. 语音消息仍可播放或保持原行为。
5. 文档卡片只影响新文档消息，不破坏旧消息。

## 25. 核心判断

这次 MVP 的关键不是做一个完整飞书，也不是让聊天气泡支持更多格式。

真正要实现的是：

> OpenClaw Bot 可以创建和维护用户空间中的持久化文档对象。

因此最终验收不能停留在 iOS Mock 页面。必须有后端真实持久化，必须有聊天卡片引用真实文档，必须能在 App 里找回、打开、编辑并保存。
